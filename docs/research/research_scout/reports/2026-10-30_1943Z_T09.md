### 1. vectorbt Sharpe returns +inf for zero-volatility series (issue #896, PR #897) and DSR kurtosis fix in v1.1.1 (PR #872) (new evidence on T09 metric-definition row)
- **Primary URL:** https://github.com/polakowo/vectorbt/issues/896 (also /pull/897, /pull/872, releases v1.1.1 and v1.2.0)
- **Date / type:** issue 2026-10-29, PR 2026-10-30 (both open, no maintainer comment); v1.1.1 2026-09-26; v1.2.0 2026-10-19. Docs/forum-grade (GitHub).
- **Summary:** The reporter CLAIMS that on vectorbt 1.2.0 the Numba Sharpe kernel returns +inf whenever std is exactly zero, whatever the mean, so a configuration that never trades scores +inf and a constant-return series scores about ±2.9e16 (rounding leaves a tiny std). A sweep ranked by Sharpe could therefore put idle configurations on top. PR #897 returns NaN for 0/0 and signed inf otherwise; a reviewer notes the near-constant case still slips through. Separately, v1.1.1 changed DSR to non-excess kurtosis, NaN-omitting and per-column horizon; release notes say results change, especially for fat-tailed or low-frequency returns.
- **Claimed effect / data:** PR #872's reproduction: DSR 0.99268 to 0.99259 at daily frequency (small); larger for monthly or fat-tailed data. No dataset; unit reproductions.
- **Strongest counter-evidence:** #897 is unmerged and unreviewed; vectorbt PRO behaviour unknown. The repo does not use vectorbt.
- **Risks:** selection artefact (idle configs ranked first) in any grid search; DSR values from before and after v1.1.1 are not comparable.
- **Data / cost / licence:** none; reading only.
- **Repo relation:** repo's own Sharpe functions guard exact zero std (cited above) but not a near-zero std; any future vectorbt adoption would need a pin and a guard.
- **Next step (needs operator approval):** a desk check (no market data) adding a unit-test case list for the repo's two Sharpe functions: all-zero returns, constant non-zero returns, and a series with std ~1e-17; record expected behaviour (raise/None). Write only the test-case list for review first.
- **Status:** UNTESTED.

### 2. skfolio CombinatorialPurgedCV defects: trailing rows never tested (PR #414, fixed in v1.8.1) and purge+embargo can empty an inner train fold (PR #454, closed pending #445)
- **Primary URL:** https://github.com/skfolio/skfolio/pull/454 (also /pull/414, release v1.8.1)
- **Date / type:** #414 merged 2026-10-10; #454 opened 2026-10-20, closed unmerged 2026-10-21 "to reopen once #445 merges". GitHub PRs.
- **Summary:** #414 CLAIMS that when `n_samples % n_folds >= n_samples // n_folds`, trailing observations fell in no test fold (e.g. row 12 of 13). #454 CLAIMS the size check `purged + embargo >= min_fold_size - 1` misses inner train folds purged on both sides, which can lose `2*purged + embargo` rows; its example (30 samples, 3 folds, purge 8) gives train folds of length [2, 0, 2]. Proposed rule: `2*purged + embargo < min_fold_size`.
- **Claimed effect / data:** toy reproductions only.
- **Strongest counter-evidence:** #454 not merged; dependency #445 not opened. Bites mainly small samples with large purges.
- **Risks:** silently untested tail = the most recent data (look-ahead-adjacent: the newest period is exactly what an OOS claim needs). Short altcoin histories are the small-sample case.
- **Data / cost / licence:** free; BSD-3 (prior knowledge, not re-checked).
- **Repo relation:** no CPCV in repo (grep above); CPCV appears as a proposal in earlier T09 rows (skfolio, purgedcv). A hand-written CPCV would face the same two edge cases.
- **Next step (needs operator approval):** if CPCV is ever pre-registered, add two acceptance checks to its contract: every row appears in at least one test fold, and every train fold length is positive after purge and embargo. Text only.
- **Status:** UNTESTED.
